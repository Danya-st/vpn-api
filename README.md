## Запуск

```bash
cp backend/.env.example backend/.env      # заполнить (APP_HMAC_SECRET: openssl rand -hex 32)
docker compose up -d --build
docker compose logs -f api
curl http://127.0.0.1:3000/healthz
```

Тесты (без сети и зависимостей, 31 шт.): `cd backend && node --test`
Покрыто: подпись приложения, клиент ЮKassa (на фейковом HTTP), разбор платежа, IP-allowlist, **весь путь вебхука**
(подделка, повторная доставка, сбой ЮKassa/3x-ui, недоплата) и бизнес-логика подписок на фейковой 3x-ui.
**Не проверено**: реальные вызовы axios → 3x-ui и → api.yookassa.ru (в песочнице нет сети и npm-зависимостей).
Первым делом прогоните тестовый платёж (см. конец документа).

## Как получить `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`

Названия пунктов меню в кабинете меняются, ориентируйтесь по смыслу; официальная инструкция — раздел «Ключи API» в справке ЮKassa.

1. Зарегистрируйтесь на yookassa.ru, подайте заявку на подключение магазина (для боевых платежей нужна проверка и юридический статус:
   ИП / ООО / самозанятый). Для разработки достаточно **тестового магазина**.
2. Кабинет → **Интеграция → Ключи API** (в справке: «Разработчикам → API-ключи»).
   - **shopId** («Идентификатор магазина») — число, показан на этой странице и в шапке магазина → `YOOKASSA_SHOP_ID`.
   - **Секретный ключ** → «Выпустить ключ» (потребует подтверждение по SMS/паролю) → скопируйте сразу, повторно ЮKassa его не покажет
     → `YOOKASSA_SECRET_KEY`. Ключ тестового магазина начинается с `test_`, боевого — с `live_`.
3. Кабинет → **Интеграция → HTTP-уведомления** (`yookassa.ru/my/http-notifications-settings`):
   URL `https://<ваш-домен>[:8443]/webhook/yookassa`, событие **`payment.succeeded`** (остальные не нужны).
   Требования ЮKassa к URL: **только HTTPS, порт 443 или 8443**, TLS ≥ 1.2.
   Если 443 занят Reality — ставьте reverse proxy на **8443**.
4. Тестовые карты и сценарии — «Тестирование» в документации ЮKassa. Тестовый магазин и боевой — разные ключи и разные URL уведомлений.

## Что не так в исходном промпте (и как сделано)

| В промпте | Реальность | Сделано |
|---|---|---|
| «Официальный npm-пакет `yookassa`» | Официальных Node-SDK у ЮKassa нет (официальные — PHP и Python). `yookassa` на npm — неофициальный, v0.1.x | Тонкий клиент на `axios` (`src/yookassa.js`): всего 2 вызова, полностью покрыт тестами, секреты в логи не попадают. Интерфейс `createPayment/getPayment` — заменить на пакет легко |
| `yookassa.handleWebhook(body, contentType)` «проверяет подпись» | **У ЮKassa нет подписи уведомлений** и такого метода нет. Документация предлагает проверять подлинность по IP отправителя и по статусу объекта | Тело вебхука **не принимается на веру**: платёж запрашивается из API (`GET /v3/payments/{id}`) нашими ключами, и дальше используется только он. Плюс проверка IP из списка ЮKassa |
| Подделка → «400» | Именно так: платёж с таким id у нас не найден → 400 | ✔ |
| «Любой 2xx — подтверждение» | ЮKassa считает доставленным **только HTTP 200**, на всё остальное повторяет 24 часа | Всегда отвечаем ровно 200 |
| Срок по `amount.value` | Хрупко при смене цен | Тариф из `metadata.plan` (его ставит только наш сервер), сумма — перекрёстная проверка; недоплата отвергается |
| `return_url: 'myvpn://payment_success'` | Во всей документации `return_url` — https-адрес | `return_url` = `https://…/payment/return` (отдаёт backend): страница сама открывает `myvpn://…` и содержит кнопку «Вернуться в приложение» |
| `getClientTraffics/${XUI_INBOUND_ID}` | Метод принимает **email**, не id инбаунда; uuid в нём нет | Как в Шаге 1: uuid и `subId` из `GET /panel/api/inbounds/get/{id}` |
| `npm i … tough-cookie dotenv cors` | Для cookie-сессии нужен ещё `axios-cookiejar-support` (одного `tough-cookie` axios не использует); `dotenv` не нужен (`env_file` в compose / `node --env-file`); CORS нужен только браузерам, Android-приложению — нет | В `package.json` есть `axios-cookiejar-support`, нет `dotenv`/`cors`; `multer` удалён (форм больше нет) |

## Эндпоинты

| Метод | Ответ |
|---|---|
| `POST /api/v1/register` `{deviceId}` | `{success, subLink, expiryTime}` (идемпотентно) |
| `GET /api/v1/status?deviceId=` | `{success, isActive, expiryTime}`; **404**, если клиента нет |
| `POST /api/v1/create-payment` `{deviceId, plan}` | `{success, paymentUrl}` — контракт для Android не изменился |
| `POST /webhook/yookassa` | 200 / 400 (мусор, подделка) / 403 (если `YOOKASSA_IP_CHECK=1` и IP чужой) / 5xx (сбой — ЮKassa повторит) |
| `GET /payment/return` | HTML-страница возврата (return_url) |

Платёж создаётся с `capture: true`, `amount: {value: "150.00", currency: "RUB"}`, `confirmation: redirect`, описание
«Продление VPN подписки на N мес.» (лимит ЮKassa — 128 символов) и `metadata: {device_id, plan}`. Для каждого POST
генерируется `Idempotence-Key`; при сетевых ошибках/5xx/202 запрос повторяется с тем же ключом.

## Безопасность вебхука

- Подлинность: повторный запрос платежа в ЮKassa (главная защита) + IP-список. По умолчанию чужой IP только пишется в лог
  (`[webhook] request from non-YooKassa IP …`): за reverse proxy `req.ip` берётся из `X-Forwarded-For`, и при неверной настройке
  прокси жёсткая проверка отвергала бы настоящие уведомления. Проверьте по логам, что реальные уведомления приходят с адресов
  ЮKassa, и тогда включайте `YOOKASSA_IP_CHECK=1`. Прокси должен **перезаписывать** `X-Forwarded-For`, а не дописывать клиентский.
- Идемпотентность: ключ `yookassa:<id платежа>` в журнале `/data`; параллельные и повторные доставки продлят подписку один раз.
- Журнал пишется только после успешного обновления 3x-ui: при сбое отдаём 5xx, ЮKassa повторит, платёж не потеряется.
- Книга платежей: `/data/payments.jsonl` (см. раздел про самозанятых).
- Платёж реальный, но непригодный (нет `device_id`, неизвестный тариф, недоплата, не RUB) → 200 и строка
  `PAID but unusable payment …` в логе: повторы не помогут, такие случаи разбирайте вручную (возврат/ручное продление).

## Самозанятый: чеки, лимиты, что проверить

- **`receipt` в запросе не нужен.** Чеки по 54-ФЗ через API ЮKassa — только для компаний и ИП, самозанятому объект `receipt` не передаётся
  (код его и не отправляет). Если `create-payment` вернёт 400 `invalid_request` про `receipt` — значит, магазин зарегистрирован не как НПД;
  проверьте тип подключения в кабинете.
- **Кто формирует чек — выясните в кабинете.** Источники расходятся: на странице ЮKassa для самозанятых заявлена автоматическая отправка чеков
  в налоговую (после входа через «Мой налог»), а в сообщении на Хабре 2025–26 гг. утверждается, что автофискализацию для НПД отключили.
  Я не смог это подтвердить, поэтому: после первого тестового боевого платежа посмотрите в «Мой налог», появился ли чек. Если нет —
  чек нужно выписывать самому. Сроки и порядок — в справке ФНС/«Мой налог» (я не налоговый консультант).
- **Книга платежей для чеков.** Каждое успешное продление пишется в `/data/payments.jsonl` (момент расчёта, сумма, тариф, платёж, устройство):
  `docker compose exec api cat /data/payments.jsonl`. Названия услуги в чеке — «Доступ к VPN, N дн.» и т.п. по вашему выбору.
  Запись не влияет на подписки; если диск недоступен, вебхук всё равно отвечает 200, а платёж восстановим по реестру ЮKassa.
- **Лимиты.** Годовой доход самозанятого — до 2,4 млн ₽ (закон). В справке ЮKassa также упоминался лимит по картам для самозанятых
  (до 100 тыс. ₽ в месяц, увеличивается по запросу менеджера) — уточните актуальное значение.
- **Тематика.** Перед боевым запуском уточните у ЮKassa, что приём платежей за VPN-подписку допустим по их правилам: это
  регулируемая область, и блокировка магазина после запуска обойдётся дороже, чем вопрос в поддержку.

## Подключение к вашей 3x-ui (Docker) — по шагам

Кто с кем разговаривает:

```
Телефон ──HTTPS──▶ ваш API (Caddy :8443 → api:3000) ──HTTP, внутри сервера──▶ панель 3x-ui (:2053)
Телефон ──HTTPS──▶ сервер подписок 3x-ui (:2096) — отдаёт vless://-ссылку
Телефон ──Reality──▶ инбаунд 3x-ui (:443) — сам VPN-трафик
ЮKassa ──HTTPS──▶ ваш API (:8443) /webhook/yookassa
```

**Шаг 1. Узнайте, как запущена ваша 3x-ui.** Выполните на сервере:

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
docker inspect <имя_контейнера_3xui> --format '{{.HostConfig.NetworkMode}}'
```

- Режим `host` (так в официальном `docker-compose` 3x-ui) и пустой столбец Ports — **вариант A**.
- Видите `0.0.0.0:2053->2053/tcp` — **вариант B** (порты проброшены).

**Шаг 2. Заполните `XUI_URL` в `backend/.env`.** В обоих вариантах это `http://host.docker.internal:2053` — контейнер API
выходит на хост через `host-gateway` (секция `extra_hosts` в `docker-compose.yml` уже есть).

- *Вариант A (host-сеть).* Панель слушает порт прямо на хосте. Но фаервол хоста (ufw) по умолчанию режет обращения
  из docker-сетей — откройте их **только для панели**, не для интернета:
  ```bash
  sudo ufw allow from 172.16.0.0/12 to any port 2053 proto tcp
  ```
  Проверьте, что снаружи порт 2053 закрыт (`ufw status`; заходите в панель через SSH-туннель
  `ssh -L 2053:127.0.0.1:2053 user@сервер`). В настройках панели поле «Listen IP» должно быть пустым или `0.0.0.0` (не `127.0.0.1`).
- *Вариант B (проброшенные порты).* Работает так же. Либо подключите оба compose к одной сети и укажите
  `XUI_URL=http://<имя_контейнера_3xui>:2053` — тогда `host.docker.internal` не нужен.

Дописывайте к `XUI_URL` путь панели, если он есть: откройте панель в браузере — всё, что после порта (например `/AbCd12/`),
входит в `XUI_URL`: `http://host.docker.internal:2053/AbCd12`. Если панель открывается по `https://` с самоподписанным
сертификатом, бэкенд его не примет — используйте `http://` и держите панель закрытой от интернета.

**Шаг 3. Остальные значения.**
- `XUI_API_TOKEN` — API-токен панели (нужна 3x-ui **≥ 3.0.2**). Создайте: *Настройки панели → Безопасность → API Token → Generate*
  (значение показывается один раз). Бэкенд шлёт его как `Authorization: Bearer …`, логин и cookie не нужны. Токен даёт **полный
  админ-доступ** — храните только в `backend/.env` (не в git, не в чатах); при утечке отзовите и создайте новый.
  Запасной вариант без токена: `XUI_USERNAME` / `XUI_PASSWORD` (двухфакторка не поддерживается). Если заданы оба — используется токен.
- `XUI_INBOUND_ID` — id инбаунда **VLESS + TCP + Reality**, в который backend будет добавлять клиентов. Узнать id — следующим шагом.
- `SUB_BASE_URL` — «Настройки панели → Подписка»: включите службу подписки; адрес = `https://<домен>:<порт подписки>/<путь>`
  без `/` в конце, например `https://vpn.example.com:2096/sub`. Этот адрес открывает **телефон**, поэтому нужны открытый порт
  в фаерволе и **валидный сертификат** (Let's Encrypt; сертификат подписки задаётся в тех же настройках) — приложение не принимает
  самоподписанные. Проверка: откройте `…/sub/<subId любого клиента>` в браузере телефона.

**Шаг 4. Запустите и проверьте связь.**

```bash
docker compose up -d --build
docker compose exec api node src/check-xui.js
```

Скрипт авторизуется в панели (токеном или логином), показывает список инбаундов с их id (стрелка `← XUI_INBOUND_ID` у выбранного), проверяет, что инбаунд — VLESS+TCP+Reality,
а при проблемах пишет причину и что сделать (фаервол, неверный путь панели, токен/пароль, `extra_hosts`).

**Шаг 5. HTTPS для API (раньше пункт 4).** Нужен, потому что (а) приложение ходит в API только по `https`, а (б) ЮKassa принимает
вебхуки только на HTTPS-порты 443 или 8443. Порт 443 у вас, вероятно, занят Reality, поэтому — 8443:
1. Создайте A-запись домена (например `api.example.com`) на IP сервера.
2. В `Caddyfile` замените `api.example.com` на свой домен. Откройте порты `80` и `8443` (`ufw allow 80,8443/tcp`).
   Порт 80 нужен Caddy один раз на выпуск и продление сертификата; если он занят другим сервисом — напишите, подберём другой способ.
3. `docker compose --profile proxy up -d`
4. Проверьте с телефона/компьютера: `https://api.example.com:8443/healthz` → `{"ok":true}`.
5. Итоговые значения: `API_BASE_URL=https://api.example.com:8443/` (Android, `local.properties`),
   `YOOKASSA_RETURN_URL=https://api.example.com:8443/payment/return`,
   URL уведомлений в ЮKassa: `https://api.example.com:8443/webhook/yookassa`.
   Если у вас уже есть nginx/Caddy — просто проксируйте домен на `127.0.0.1:3000` и пропустите `--profile proxy`.

**Шаг 6.** `APP_HMAC_SECRET` в `backend/.env` и в `local.properties` Android — одна и та же строка.

## Контракт подписи для Android

```
X-Device-Id:     <UUIDv4>
X-Timestamp:     <System.currentTimeMillis()>
X-App-Signature: hex_lowercase( HMAC_SHA256(key = APP_HMAC_SECRET, msg = deviceId + timestamp) )
```

## Проверка платежа в тестовом магазине

1. Тестовые `YOOKASSA_*` в `.env`, `docker compose up -d --build`, URL уведомлений в кабинете тестового магазина.
2. В приложении: истечь подписке (или «Продлить подписку») → тариф → Custom Tab с формой ЮKassa → тестовая карта.
3. В логе backend: `[payment] created …` → `[webhook] yookassa:<id> device=… plan=…: applied`.
4. Возврат в приложение: «Подписка продлена».
